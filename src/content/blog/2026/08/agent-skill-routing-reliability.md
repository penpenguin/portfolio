Agent Skillは、手順を`SKILL.md`へ書けば終わりではありません。「Agent Skillを作って配っても正しく使われない理由」は、配布後に起きるずれを、Skillの選択、実行環境、出力の読まれ方という三つの面から捉えた記事です。なかでも厄介なのは、誤った使い方でもAIがそれらしい成果物を返し、失敗が表に出にくい点。ここはSkillの書き方だけでは埋まりません。([橋本商会][1])

## 本文より先に、入口が評価される

Agent Skillsの仕様は、段階的に情報を読み込む「Progressive disclosure」を採用しています。起動時に常時読み込まれるのは、各Skillの`name`と`description`だけ。タスクに合うと判断された後で、ようやく`SKILL.md`の本文がロードされます。つまり、本文に丁寧な利用条件を書いても、入口で選ばれなければエージェントには届きません。([仕様][2])

似たSkillが並ぶほど、`description`は単なる紹介文ではなくルーターになります。「何ができるか」に加えて、「どんな依頼で使うか」「隣接するSkillとの境界はどこか」まで短く示す必要があります。公式ガイドも、命令形で利用場面を書き、実装の仕組みよりユーザーの意図へ寄せるよう勧めています。([description最適化ガイド][3])

ただし、印象的な単語を足すだけでは安定しません。ガイドが提案するのは、発火すべき依頼と発火してはいけない依頼をそれぞれ8〜10件ほど用意し、近い領域の紛らわしい依頼も混ぜる方法です。同じ依頼を複数回試し、発火率を見る。Skill選択を文章の勘だけに任せず、ルーティングのテストとして扱うわけです。

## 実行前と実行後にも観測点を置く

入口を通っても、想定したモデルやツール、ネットワーク権限がなければ手順は崩れます。仕様には、対象製品や必要なシステムパッケージ、ネットワークアクセスなどを書ける任意の`compatibility`フィールドがあります。([仕様][2]) とはいえ、メタデータへ書くだけで環境が揃うわけではありません。元記事が提案するように、処理の冒頭で前提を確認し、不足があれば黙って代替せず報告する仕組みが要ります。

実行後の観測も同じです。使ったモデル、途中で起きた問題、完了した検証をレポートへ残せば、「何か出た」状態と「想定どおり動いた」状態を分けられます。長い報告書は、表示先によって先頭だけ、あるいは末尾だけ読まれることもある。結論と異常の有無を短く置き、詳細は後から追える形にするほうが堅実です。([橋本商会][1])

Skillを配るなら、配布物だけでなく運用の約束も渡したいところです。誰がSkillを選ぶのか、必要な環境をどこで確かめるのか、発火をどう試験するのか、失敗をどの欄へ残すのか。この四つが決まって初めて、「インストール済み」を「使える」に近づけられます。
